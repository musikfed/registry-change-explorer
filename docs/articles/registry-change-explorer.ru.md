# Зачем администраторам Windows нужен Registry Change Explorer

Администратор Windows часто знает, **где искать**, но гораздо сложнее понять, **что именно изменилось**.

Установили программу, обновили драйвер, применили политику, изменили настройку оболочки или разбираетесь, почему система начала вести себя иначе — в Registry могут появиться десятки и тысячи изменений. `regedit` отлично подходит, когда известен конкретный путь. Но расследовательский вопрос обычно другой:

> Что изменилось между рабочим состоянием и состоянием после изменения системы?

Из этого вопроса и выросла идея **Registry Change Explorer**.

## Основная идея

Проект не строится вокруг автоматического изменения Registry. Центральный сценарий безопаснее и полезнее для диагностики: **проиндексировать, посмотреть, сделать снимок, сравнить, объяснить**.

Желаемый workflow выглядит так:

1. Создать **Снимок A** до контролируемого изменения.
2. Установить программу, обновить драйвер, применить политику или изменить настройку Windows.
3. Создать **Снимок B**.
4. Показать понятный diff: добавленные, удалённые и изменённые ключи и значения.
5. Отфильтровать изменения по hive, path, типу значения или типу изменения.
6. Экспортировать результат как диагностический отчёт.

Такой инструмент может быть полезен системным администраторам, support-инженерам, разработчикам, QA, командам упаковки ПО, специалистам по расследованиям и продвинутым пользователям Windows.

## Что уже умеет прототип

Публичный прототип специально начинается в read-only режиме. Он умеет обходить Registry, сохранять локальный SQLite-индекс и выполнять поиск без полного рекурсивного обхода реестра при каждом запросе.

Интерфейс объединяет дерево Registry и две панели навигации. Приложение работает только на localhost. Есть синтетический demo mode, поэтому для демонстрации интерфейса и скриншотов не нужно публиковать данные реального компьютера.

## Зачем нужен индекс

Работа с Registry часто идёт сериями запросов: имя продукта, CLSID, служба, фрагмент пути, имя драйвера. Повторный рекурсивный обход Registry для каждого поиска — неудобная модель взаимодействия.

Локальный индекс меняет подход: дорогая операция чтения выполняется при синхронизации, а навигация и поиск становятся быстрыми. Кроме того, индекс — естественная техническая основа для хранения нескольких снимков и их сравнения.

## Какую админскую функцию хотелось бы увидеть в экосистеме Windows

Более крупная идея — **Registry Change Explorer** как административная возможность: безопасно отвечать на вопрос «что изменилось?», а не пытаться автоматически решать, что пользователю «не нужно».

Полноценная версия могла бы включать:

- именованные снимки Registry;
- сравнение «до / после»;
- добавленные, удалённые и изменённые значения;
- старое и новое значение рядом;
- фильтры по hive/path;
- экспортируемые отчёты;
- дополнительный контекст контролируемой установки/настройки;
- read-only режим по умолчанию;
- явный backup/recovery workflow перед любыми будущими изменениями.

Концепция могла бы органично смотреться среди Windows admin tools, экспериментальных PowerToys-утилит или рядом с Sysinternals-подходом к диагностике. Этот репозиторий — независимый прототип, а не официальный проект Microsoft.

## Безопасность — часть продукта

Инструменты Registry требуют осторожности. Публичный прототип не должен начинаться с разрушительных решений за пользователя. Просмотр и diff полезны сами по себе, даже если операции записи никогда не появятся.

Если запись будет добавлена позднее, модель безопасности должна быть видна пользователю: точное действие, backup, preview, явное подтверждение, audit trail и понятное восстановление.

## Что дальше

Ближайший технический этап — SQLite FTS, затем версионируемые снимки и настоящий diff engine. После этого начинается самая интересная UX-задача: превратить большой низкоуровневый набор изменений в объяснение, которое администратор понимает за несколько секунд.

Если вы работаете с Windows administration, deployment, packaging, troubleshooting или developer tools, важнее всего обратная связь по самому workflow. Главный вопрос:

> Что должно быть в сравнении Registry «до / после», чтобы вы действительно доверяли ему в ежедневной работе?
